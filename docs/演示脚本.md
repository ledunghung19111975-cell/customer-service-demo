# 面试演示脚本｜V3.2

产出 Agent：Codex

建议主线约 8–10 分钟；流程异常和完整知识整改作为追问时的扩展。按客户的一次服务推进，不从十个菜单逐页介绍。

## 演示前准备

在项目目录启动 `python3 -m http.server 8768 --bind 127.0.0.1`。运营工作台地址为 `http://127.0.0.1:8768/`，客户页面地址为 `http://127.0.0.1:8768/?view=customer#playground`。使用同一浏览器、同一标签页，切换角色时在地址栏打开相应地址，避免多个标签页同时修改同一工作空间。

准备空白业务环境时，先在“系统设置”导出需要保留的数据，再展开“高级维护”，选择“清空业务记录并恢复配置”并确认。它会恢复内置知识和接待配置，清空会话、事项、工单和输入草稿，不会重新生成历史样例会话。主线从空白环境开始创建自己的咨询记录；演示前完整自走一遍，确认页面没有本地保存警告。

样例订单是 `SO20260926001`、`SO20260926002`。示例规则、坐席、工单和结果全部虚构，不要输入真实订单、个人信息、密钥或收款信息。工单号与事项号随操作动态生成，讲解时使用当前页面显示的编号，不照背截图编号。

开场可以这样说：

> 这套原型验证的是一条完整客服链路：客户咨询后，能查信息、提交需求，由人工和工单继续处理，最后确认结果。后台能维护知识和流程，并把服务中发现的问题改回系统。当前是规则驱动的前端演示，真实模型和业务接口是下一步接入范围。

## 主线一：客户进来之后发生什么

### 第 1 步｜入口与有依据的规则咨询，约 1 分钟

打开客户页面，标题为“青禾生活 · 在线客服”。指出“服务规则”“订单物流”“申请售后”三个入口，以及“我的订单”卡片。浏览页面不会新增会话；选择服务或订单卡片上的操作会立即发送对应咨询。

为展示自定义问法，点击“开始咨询”，在输入框填写：

```text
不要转人工，我只问退货规则
```

发送后应保留机器人接待状态，出现示例规则和来源。打开来源看标题、版本、出处和适用范围，再关闭。点击该知识事项的“这项已解决”。

讲解重点：

> 这里不是看到“人工”两个字就转接，也不会因为问退货就强制索要订单号。回答需要依据，确认只对应这一项，不代表后面所有事情都解决了。

### 第 2 步｜一条消息里的查询与办理分开，约 1 分钟

在同一会话输入：

```text
查物流 SO20260926001，再申请退货
```

页面新增“查询订单与物流”和“申请售后处理”两个事项；上一条规则事项仍以已解决状态保留。查询有订单卡片并待确认；售后仅展示受理入口，尚无新工单，更没有退款。

点击查询事项的“这项已解决”，售后仍未解决。可指向两个状态说明：

> 同一个客户说了两件事，要分别记录结果。查到物流不能证明退货办好了。我把会话、服务事项和工单分开，避免一个结束按钮把所有问题都算作解决。

### 第 3 步｜先确认再受理，约 1 分钟

在售后事项点击“填写并确认售后申请”。核对预填订单号，问题描述填：

```text
外盒破损，商品未使用，配件齐全，请核实退货处理方式。
```

点击“预览并确认提交”，查看二次确认中的事项、标题、订单和描述。可以先取消一次，证明取消不建单，再重新预览并“确认提交”。

返回客户窗口，受理卡片显示实际生成的工单编号和待分配状态。点击受理卡片的“查看当前进度”将打开已有记录，不创建重复工单。

> 受理是一个有外部影响的动作，不能仅因为模型理解了意思就执行。先给用户检查，再登记；登记成功也只表示需求被接住，不表示售后审批或退款到账。

### 第 4 步｜人工接续而不是让客户重说，约 1–2 分钟

客户页面点击“转人工”。在同一标签页地址栏打开 `http://127.0.0.1:8768/#playground`，进入后台“渠道预览”。展开当前会话的“会话执行记录”，点击“查看坐席会话”，确保接续的是刚才这次咨询。

在会话中心点击“接管会话”。看右侧已有的售后事项、订单线索、摘要、工单和原始聊天。发送：

```text
我已看到订单线索和外盒破损的描述，会继续核实。后续需要补充的内容和处理进度都会记录在这张工单中。
```

点击“查看接待预览”查看人工回复，机器人没有抢答；再通过“打开客户页面”查看客户入口。点击“结束咨询”并确认，说明聊天结束但工单继续。

> 人工接手时拿到的是结构化事项和完整上下文，不是重新问一次“你遇到了什么问题”。人工接管以后有明确回复权，机器人只保留辅助边界。

### 第 5 步｜结束聊天后仍可补充与跟进，约 2 分钟

在同一标签页地址栏打开 `http://127.0.0.1:8768/#tickets`，进入工单中心，打开刚创建的工单。负责人选“客服小林”，下一状态选“处理中”，客户可见说明填“已由专员核对订单线索”，更新。

再次打开这张工单，下一状态选“待客户补充”。客户说明填：

```text
请确认商品是否使用、外盒是否破损、配件是否齐全，用于核实本次售后需求。
```

内部备注填“内部演示：需要核对当前工单资料”，更新。打开客户页面，在“我的咨询”中回到原咨询，从“我的服务事项”打开该工单，说明内部备注没有展示给客户；即使聊天已结束或已发起新咨询，原工单仍可继续跟进。提交：

```text
商品未使用，外盒破损，配件齐全。
```

工单恢复处理中，聊天保持已结束。回工单中心选择“已完成”，只填客户可见说明并尝试更新，会被要求补充结果证据。然后填写：

客户可见说明：
```text
已核实本次演示处理方案，请确认当前结果；本演示不执行真实退款。
```

内部结果证据：
```text
DEMO-RESULT-001：模拟业务处理结果已核验，非真实退款流水或到账凭证。
```

更新后，售后事项是“待结果确认”，不是直接已解决。回客户窗口点击该事项“这项已解决”，才进入已解决。

> 工单完成要求有结果说明和证据；客户的事项结果另行确认。内部协作记录和客户通知分开，避免把客服备注直接发给用户。

## 主线二：后台不是只能展示，配置要影响服务

### 第 6 步｜知识草稿与发布，约 2 分钟

在后台进入知识库，编辑“七天无理由退货规则”，保留原内容，在答案末尾增加：

```text
演示补充：申请前请先核对商品是否属于不适用此规则的范围。
```

仅“保存草稿”。新建一个客户会话询问“七天无理由退货有什么条件？”，此时仍显示旧版答案。回知识库找到该条目，点击“草稿回归”，查看标准问题及边界行为的实际结果，再“发布此知识”并确认。

回刚才的会话再问一次，相同会话可以用新发布知识；第一次回答保留旧引用快照，不被静默改写。

> FAQ 不是一张静态问答表，还需要来源、范围、有效期、草稿与现行内容。发布前有测试，发布后前台确实变化；知识版本可以实时更新，但历史回答必须能够追溯。

主线到此结束。不要用本地“客户已确认事项”计算真实业务提升。对下一阶段可说明：接一个真实只读工具、接真实模型与知识检索、补服务端权限和持久化，再做固定口径试点。

## 扩展一：画布编排与生效版本，约 4 分钟

先新建会话，查询 `SO20260926001`，记录当前流程版本，再进入流程编排。

1. 从节点库拖入“条件判断”，移动到“事项分流”和“订单查询”附近。保留条件“客户问题／包含／加急”。
2. 将“事项分流”的“订单查询”输出连到条件节点输入。原线会被替换。把“满足条件”连到“转人工”、“不满足”连到“订单查询”。也可依次点击两个端口连接。
3. 等待结构提示为完整。分别试问 `加急查询订单 SO20260926001` 和 `查询订单 SO20260926001`：前者转人工，后者返回订单。观察不同高亮路径，点击步骤查看输入与输出。
4. 选中一条连线后删除，查看断点提示，再重新连好。尝试将回复节点接回分流节点，页面应拒绝循环且保留原线。刷新后图和参数仍保留。
5. 执行“运行发布回归”，再“发布流程”。点击“新建会话验证发布版”，再次发送加急查询，应沿新分支转人工；先前会话仍使用原版本。

草稿修改会清除旧试问结果并使发布回归失效；仅调整位置不影响回归。单条“运行测试”不替代发布依据。若演示查询超时，在“草稿测试”的“订单查询测试响应”中选择“查询超时”，运行测试并观察失败出口。该响应仅注入本次测试副本，不改变草稿或发布版本；测试后可切回“正常查询”。

在“系统设置”的“接待设置”中，将“服务组状态”改成“忙碌”，填写变更原因并点击“保存接待设置”。客户转人工时显示排队，不出现凭空编造的等待分钟数。再改成“离线”，已有会话下一步也读取当前状态。

恢复“在线”，并把“订单查询”改为“停用”，填写原因后保存。旧流程会话也不能继续调用已停用工具。说明流程版本稳定与实时安全限制是两套不同规则。演示完将服务组状态恢复“在线”、订单查询恢复“启用”并保存；流程可从历史版本“恢复为草稿”，回归后发布，生成新版本而不是覆盖旧记录。

## 扩展二：知识缺口到整改验收，约 3–4 分钟

建议在流程正常、工具可用、知识尚未新增礼品卡规则时演示。新建会话发送：

```text
礼品卡可以分多次使用吗？
```

会产生知识未命中线索并转人工。进入质检与日志，按本次会话编号打开线索，不误选初始化样例。复核结论选“已确认”，说明填：

```text
业务确认这一问题应纳入服务范围。此次转人工是合理兜底，整改对象是知识覆盖缺口，不是把拒答判成违规。
```

责任人填“客服运营”，根因填“知识覆盖缺口”，保存。点击“转为 FAQ 草稿”，填写以下内容：

| 字段 | 演示内容 |
| --- | --- |
| 知识标题 | 礼品卡分次使用规则 |
| 标准问题 | 礼品卡可以分多次使用吗？ |
| 分类 | 通用服务 |
| 匹配关键词 | 礼品卡,分次使用 |
| 标准答案 | 青禾生活虚构演示：礼品卡支持按余额分次使用，不支持提现；实际资格需人工核实。本演示不执行余额查询或扣减。 |
| 适用范围 | 青禾生活 |
| 维护人 | 客服运营 |
| 来源说明 | 青禾生活虚构演示规则，仅用于验证知识整改流程，不对应真实商家政策。 |
| 生效时间 | 保持当前时间或更早的有效时间 |
| 失效时间 | 留空 |

保存草稿，草稿回归后发布。在原质量问题中点击“原问题与边界回归”。有匹配的通过记录后填写验收说明，再点击“验收并关闭整改”。没有关联修订知识、没有发布或未通过回归时，不能直接关闭。

> 这一步说明产品不止完成一次回答，还需要让运营知道哪里缺、由谁改、改了什么、原问题是否真的变好。本地回归只能验收演示规则，真实生产问题仍需线上证据。

## 扩展三：面试官现场追问的边界

“没有订单号，只想了解条件”：新会话输入“没有订单号，想了解退货条件”，应直接给有来源的示例规则。

“问到一半突然插问”：先“帮我查订单”，再“保温杯怎么清洗？”，最后发送 `SO20260926001`（也可以说“我的订单号是 SO20260926001”）；原订单采集要能继续，不另建事项。

“客户说没解决”：打开已完成工单，客户提交未解决异议。工单保留已完成并标为异议待核，事项立即回到待人工。坐席提供证据后重开原工单；第一次受理时间不重置。

“人工占用后另一个坐席能不能抢答”：接管后切换演示坐席，回复框应禁用。说明这是本地校验，真实并发要在服务端做原子接管，本地校验不能证明多浏览器竞争安全。

“这是 Agent 吗”：当前是可编辑的无环画布和本地规则执行器，用它验证状态与协作边界。真实 AI 可以替换诉求理解、字段抽取和回答组织，但不能绕开授权、确认、状态和证据门槛。

## 演示卡住时先核对

发不出消息时先看会话是否结束、是否等待人工或已经由人工接管；不是所有输入都应得到机器人回复；机器人没作答就转人工时，看执行轨迹是否为“没有达到作答门槛”，这是知识覆盖缺口，按扩展二补知识，不是故障。回归或发布被阻止时，检查是否改过草稿／知识、知识是否在生效区间、是否已有匹配测试记录；S 开头的用例失败，说明这次改动让存量问句的答案来源变了，先处理重叠的关键词或标准问题。接不了会话时看实时状态、容量和当前演示坐席。

不要通过开发者工具跳过校验来完成演示。无法解释的情况保留输入与错误，按问题复核路径检查。需要重新准备时，先导出记录，再按“演示前准备”清空业务记录；清空不会恢复历史样例会话。
