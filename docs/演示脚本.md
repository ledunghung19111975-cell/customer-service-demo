# 智能客服演示脚本

适用入口：旧电商与通用 V4（`ecommerce-v1.html`）；当前 V2 路线见 [V2 本地验收](v2/本地验收.md)。

产出 Agent：Codex。集成、主写、参与与最终收敛 Agent：Codex。用户附件原始产出平台未标明。

## 电商演示准备

运行 `python3 run.py --no-open`，打开 [电商客服](http://127.0.0.1:8768/ecommerce-v1.html#customer)。在同一标签页切换工作区；需要全新样例时使用独立测试来源，不清理日常数据。通用 V4 使用 `?data=v4` 进入；旧电商参数 `?data=ecommerce` 继续可用。所有订单、材料、金额与业务回执均为虚构样例。

### 1. 规则、商品与两包裹

发送 `你好`、`谢谢亲`、`回头见`，观察不建事项、不转人工，告别只给回应。发送 `嗨，查下订单 EC-SO20261005001`，核对商品与两个包裹，不转人工。发送 `保温杯退货规则是什么？`，核对规则版本、¥129.00、经理审核与寄回验收要求，确认只是咨询。点击订单的“查看支付与包裹”，观察杯子 ¥129、收纳袋 ¥49、整单 ¥178，以及杯子签收、收纳袋在途的两个包裹。

### 2. 双商品诉求与主动确认

发送 `收纳袋没到，保温杯破了想退`，进度出现两个商品事项，均未办结。选择杯子的“申请售后”，原因填 `杯体破损，希望退货退款`，材料使用 `DEMO-DAMAGE-001`。预览一件 ¥129，取消不会受理；重新预览并“确认提交本次申请”后进入待经理审批。收纳袋不生成杯子的退款申请。

### 3. 审批、寄回和执行结果

1. 运营后台切到服务经理，在待审核申请选择“查看并审核”，填写依据并批准。批准时尚未退款；另一个新申请可演示要求补件或拒绝。
2. 客户杯子事项点击“填写寄回运单”，输入 `DEMO-RETURN-001`。运营后台切系统管理员，在数据维护“演示事件面板”依次提交“模拟仓库收货”“模拟验收通过”。收货时不能直接退款。
3. 客服工作台由客服 01 接管会话，在杯子事项“核对并提交模拟退款”。保留原请求号。管理员可先提交“模拟退款未知”；客服“核实原退款请求”，观察事项仍未完成、没有第二请求。
4. 管理员提交“模拟退款成功”，金额仍为 ¥129。提交“模拟通知发送失败”，退款成功保持；再提交“模拟通知发送成功”补救。客户主动“确认问题已解决”才出现已确认。
5. 客户“仍需帮助”，填写未到账等异议，原事项重开，退款成功与已用金额保持。负责客服用“记录异议复核结果”提交原结果核实依据；不会再次退款。

### 4. 人工接续与安全退出

在收纳袋事项由客服 01 发起交接给客服 02；待接收期间仍由客服 01 负责。切客服 02 接收，核对摘要、当前负责人和反馈时间，发送“本事项公开回复”。会话接待人与各商品事项负责人独立，其他商品不随本次移交改变。

拒接保留原责任；到期后经理在概览“核对超时交接”，原负责人可重新安排。未决事项可安排下一次反馈；关闭沟通后原办理人仍可发送事项回复。

客户申请撤回只记录请求。退款未执行时管理员的安全撤回确认可释放未用占用；退款未知或处理中不能释放。失败退款先补入已安全终止的高版本回执，再确认撤回；已成功退款不能撤回已用金额。

### 5. 流程评测、整改与看板

知识运营打开知识页，“运行流程评测”对已发布版本或当前草稿执行 12 条多轮业务分支。知识与接待策略保存草稿、运行回归、发布确认；商品范围、规则、事实或有效期变化必须复测。商品售后政策金额和前置条件由结构规则生成，一般说明文案不会覆盖执行规则。

服务问题由经理确认根因，知识类关联知识版本；路由、业务、办理、协作或通知类关联整改说明与失败场景。通知整改须原通知成功送达；双商品原问题须两事项均有结果；示例全绿不能代替原问题证据。

服务经理在概览查看全部有效事项、已查询、已受理、办理完成、退款成功、客户确认、AI 独立完成、人工参与、等待中与结果未知。点击卡片下钻对应事项并核对结果；含人工审批、验收或财务处理的杯子退款不算 AI 独立完成。

## 通用 V4 参考演示

以下路线对应通用 V4 的工单模型，可用于查看保留的通用能力。

## 演示准备

运行 `python3 run.py --no-open`，打开 [V4 客户服务](http://127.0.0.1:8768/ecommerce-v1.html?data=v4#customer)。使用同一标签页切换工作区，避免多个页面同时修改。“手机端演示”与客户服务共用客户角色和当前记录，不新增角色。已存在业务记录时复用相应记录；需要全新样例时使用独立测试浏览器配置，不清空原有数据。

演示中客户为客户 001，客服可切换客服 01、客服 02，运营后台可切换服务经理、知识运营、系统管理员。面客页面为“服务中心”，咨询窗口显示“在线客服”。角色选择只模拟岗位行为。开场可说明：“这个原型展示客户咨询、人工处理和运营改进怎样接续。问答与订单都在本地模拟，没有接入真实模型或退款系统。”

## 1. 有来源的答复与独立反馈

1. 在客户页点击“新咨询”，发送 `保温杯怎么清洗？`。
2. 查看答复和来源，打开引用，核对知识原文及版本。
3. 先切到运营后台，以服务经理查看“服务概览”：已形成答复的问题计入“处理完成”，客户确认尚未增加。
4. 回到客户页，通过“历史咨询”找回该问答，点击“已解决”，再查看概览。

说明重点：一条普通咨询可以完成答复，无需创建工单；客户明确确认与服务方处理完成分开记录，沉默不会被补记为认可。

## 2. 手机咨询、结构化申请与取消预览

1. 新建咨询，切换“手机端演示”，确认仍是同一咨询，手机靠左、右侧留白。发送 `查物流 SO20260926002，再申请换货，商品颜色不符`。该订单为客户 001 的棉麻收纳袋，初始样例未建售后工单。
2. 查看物流结果和售后入口，打开手机框内申请表，核对本人订单、金额、状态、换货类型及原话原因；换货要求填写 `更换同款同规格`，补充说明填写 `先通过站内回复确认`。
3. 进入核对页，再“返回修改”，确认各字段保留；再次预览后取消，核对未新增工单。
4. 重新进入申请，确认草稿保留，再预览并确认，记录实际生成的工单编号。从“服务进度”打开原单，核对申请字段、受理时间与公开记录。
5. 切换客户服务与手机端，确认会话和工单不重复；在输入框写一段未发送文字，切换后核对草稿仍在。

说明重点：查到物流与受理售后分别记录。只有明确确认才受理；申请已受理不代表资格已批准或退款完成。若相同问题已有未完成工单，继续原工单。

## 3. 当场处理，不强制建单

1. 新建咨询并点击“联系人工”。
2. 切到客服工作台，在“待接待”找到客户 001 的新会话，使用客服 01 接管。
3. 发送一条公开回复，再填写一条内部备注；回到客户页核对只显示公开消息。
4. 回到客服工作台，查看右侧八个固定 SOP 节点和退换货四个常显子步骤；展开“记录处理结果”，点击“记录结果”，打开“记录当场处理结果”表单。客户可见结论可填 `已核对使用说明：建议用软布和中性清洁剂清洗，避免使用钢丝球。`，内部依据填 `核对本地样例知识 KB002 的已发布使用说明。`。
5. 提交结果后点击结束沟通，核对小结和实际未完成项。没有遗留项时保存关闭记录，再回客户页反馈“已解决”。

说明重点：客服先取得接待权，再形成可追踪结论。公开结论与内部依据分开保存；有结果后可结束本次沟通，客户反馈继续独立记录。

## 4. 工单补充、转派与异议续办

1. 在客服工作台“工单处理”领取第 2 段演示创建的工单，选择“请客户补充”，公开说明填 `请补充申请原因及商品状态，便于继续核实。`。
2. 回到客户页“服务进度”，提交补充信息；核对原工单继续办理。
3. 切到服务经理的“团队协同”，将工单转派给客服 02；切回客服工作台并选择客服 02。
4. 打开工单，选择“记录办理结果”，填写公开说明 `已完成样例信息核对，处理方式已说明。`，内部依据 `依据本地订单与客户补充记录核对，仅记录演示结果。`。
5. 回到客户页查看结果，点击“仍需帮助”，填写 `还有一项处理说明需要进一步确认。`。
6. 核对原工单恢复办理，首次受理时间和历史记录保留；概览不再将该问题计入当前已完成。

说明重点：同事负责的工单仅作为相关上下文查看；办理权跟随负责人。客户异议继续原问题，不通过重复建单隐藏此前处理过程。

## 5. 动态建议与有限 AI 续答

1. 新建咨询并联系人工，在客服工作台由客服 01 接管。回客户页发送 `保温杯怎么清洗？`，再切回客服工作台，选择对应问题，查看动态建议及来源。
2. 先在公开回复写一句手工开场，再点击“插入公开回复”，分别检查取消和追加，确认内部备注没有被带入公开草稿。核对后发送，查看消息保留的知识引用。
3. 客户继续发送 `七天无理由退货有什么条件？`。在客服工作台明确开启“忙时 AI 续答”，保持输入框不编辑，等待 30 秒后查看“AI 协助”回复；核对它未被记为人工亲自回复。
4. 客户发送下一条有依据的问题，保留该次授权时最多再续答一轮。没有新消息时不能自行连续发送，达到上限后需重新授权。
5. 在新的待答问题上再次开启续答，立刻输入人工回复，核对自动续答暂停且草稿保留。再查看无可靠知识的问题，确认提示待核实，不生成政策或退款承诺。

说明重点：动态建议仅协助人工写回复；自动续答有独立授权、等待和轮数控制。资料收集不等于受理，普通回复和 AI 消息都不代表问题办结。

## 6. 离线、遗留安排、回访与历史快照

1. 保持一段由客服 01 接管、尚有未完成问题的会话。在手机端写下未发送草稿，点击“模拟离线”；确认草稿保留、发送不可用。切换 Tab 不改变连接状态。
2. 回客服工作台，查看客户离线提示，点击结束沟通。填写小结，为每条未完成项填写原因和安排；可以关联已分配的原工单，或建立跟进工单，填写未来目标时间。同单共用多个节点时采用同一目标时间。
3. 对需要联系的问题勾选回访，填写目的、未来计划时间和可选内部备注，核对北京时间 UTC+08:00。先取消确认输入保留，再打开并保存关闭记录。
4. 在“工单处理”的“待回访”筛选查看后续任务。纯跟进任务只承接责任，不会把未正式确认的售后标成登记完成；售后资料核对齐全后，仍要经过结构化预览确认。
5. 服务经理转派回访所属工单给客服 02，再用客服 02 登记“未接通，重新安排”，填写下次未来时间；客服 01 不再能修改该回访。回访本身不自动办结业务。
6. 回原会话的关闭历史，核对当时节点状态、工单关联、原回访目的、负责人和时间仍保留。随后从手机端恢复在线，继续原咨询，核对历史快照未变、旧草稿未被自动发送。

说明重点：关闭的是本次沟通，遗留责任落到可追踪任务。没有有效安排、依赖已变化或保存失败时，会话不能半关闭，输入也不应丢失。

## 7. 知识缺口到原问题验收

1. 使用初始样例中的 `礼品卡可以分多次使用吗？` 线索，或在新咨询发送该问题生成线索。
2. 服务经理进入“质量复核”，确认问题，依据填 `当前已发布知识没有覆盖该样例问题。`，根因填 `缺少礼品卡使用次数说明。`。
3. 知识运营进入“服务改进队列”，对该线索新增知识。标题填 `礼品卡使用说明`，标准问题与正例保持原问句，关键词填 `礼品卡,分多次,使用`；答复填 `本演示样例允许礼品卡分次使用，具体余额由人工核对。`；来源填 `演示用礼品卡规则`；反例填 `我要查订单`，生效日期选当前日期。
4. 保存草稿、运行回归，逐项检查后发布；回到改进队列关联这条已发布知识。
5. 服务经理执行“验证原问题并验收”，填写验收说明。系统原样重放原问题并运行全量规则回归，通过后才关闭线索。

说明重点：线索先复核，知识先验证再发布，验收使用客户原话。演示答复是人为编制的虚构政策，不能用于真实商家承诺。

## 8. 策略与运行边界

1. 知识运营打开“接待策略与测试”，查看人工触发词、售后受理开关和当前发布版本。
2. 在“草稿测试”输入 `查物流 SO20260926001`，勾选本次查询失败，运行单条测试，核对显示失败分支且未创建业务记录。
3. 修改策略时先保存草稿、运行回归，再发布。解释新咨询保存新策略版本，已有咨询保留开始时的策略。
4. 系统管理员打开“接入与运行”，查看本地能力与未接入项；在“数据维护”查看 JSON 导出入口。需要验证导出时，另行确认下载文件落盘并可再次读取，不以按钮出现代表文件已交付。

说明重点：策略是有限配置；规则回归不等于大模型效果评测。导出保存本地数据，不提供生产同步或恢复导入能力。

## 交付口径

演示完成可以说明已展示咨询、接待、办理与整改的协作路径。测试与实际验收范围以 [验收矩阵](验收矩阵.md) 和 [SOP/手机端验收证据](../tests/evidence/sop-mobile-review.json) 为准，不把演示步骤本身当成已通过的验收记录，不引用历史模块总测试数证明 V4 覆盖。

真实模型、设备在线状态、退款履约与通知均未接入。真实 iOS 键盘、设备网络、推送以及导出文件落盘再读取不作为已经验证的演示结果。
