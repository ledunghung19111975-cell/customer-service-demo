## 五、资深智能客服产品经理视角的最终判断

修订版可以沿一条真实感较强的服务过程检查产品机制：先识别任务，再采集与查询，办理先确认，人工有上下文，工单有责任与证据，结果按事项记录，运营改动能回到服务。相比单纯问答页或工单 CRUD，这些连接更能体现客服产品设计能力。

关键取舍是合理的：不为演示扩展自由画布和一批空后台，不让自动退款成为没有约束的亮点；先把 FAQ 治理和固定模板做成可操作闭环。保留现有技术路线也使变化能够与原项目逐项比对。

但完整性只在声明的范围内成立。任意自然语言、多行业适配、细粒度技能路由、并行子工单、通用整改、成熟经营指标都没有实现。继续推进时，应优先取得真实场景与数据，而不是只补更多前端页面。

## 六、面试官视角的最终判断

这套材料适合用于说明候选人对智能客服从问答到服务执行的理解，以及把产品约束转成状态、页面和验收的能力。演示可以支持对需求拆解、边界设计、异常承接、知识运营和可测性的讨论；不能代替真实生产项目或岗位所需的上线经验。

最值得现场验证的是三件事：客户说完后究竟还有哪些事项没有完成；后台的改变是否真的影响前台且有版本依据；故障、异议和未解决反馈是否还能找到责任和后续路径。V3 给出了可操作证据，不再主要依赖方案表述。

仍需候选人补充的证据包括真实访谈与优先级依据、真实模型和检索评测、数据及接口条件、实施协作经历和固定口径的服务效果。面试中应清楚区分亲历项目、原型设计和未来目标，不能将样例客户、前端测试或模拟证据包装成实绩。

因此，本轮结论是：**可以作为智能客服产品经理面试的场景化演示作品；尚不是生产级平台，也不能单独证明真实 AI 效果或商业交付能力。** 最有效的展示方式是主线演示加一两个异常追问，而不是逐页展示功能数量。

## 七、保留问题与后续优先级

近期前端完善可关注更完整的事项撤销、并行任务、字段字符计数统一、知识更广的冲突场景、更多筛选与可访问性、浏览器实际存储和多标签页保护。当前文档已标明这些边界，不用临时文案假装实现。

真实试点优先级高于继续堆功能：确认一个客户、一组问题、知识责任人、一个授权只读工具和人工承接，补服务端身份与持久化后再接模型。达到这些条件后，才有基础讨论服务质量、成本和扩量。

## 2026-09-28 三轮复审：路由与知识治理（V3.1）

产出、主写与最终收敛 Agent：Claude。审查和修复由同一 Agent 完成，未启用多 Agent 独立审查：本会话用户未要求，平台默认不允许自行启动子 Agent。独立复跑待非修复 Agent 按桌面工作台交接记录 `2026-09-27-T138客服Demo代码审查.md` 执行。

触发依据：面试官现场换一种说法试用时，路由与知识检索会给出错误或重复的结果，而且发布回归发现不了。审查结论为 P0 0／P1 5／P2 6。本轮修复全部 P1，P2 未改。

1. **否定转人工只认固定句式。** 否定词补上“不想／不／没必要”等，并对所有配置的人工触发词生效；“人工就不用了”这类句末否定、“人工智能／人工费／人工成本”这类构词都不再转人工。质问或反问（“为什么不转人工”“怎么还不给我转人工”“……吗？”）仍然转人工，因为漏转一个着急的客户比多转一次代价高。
2. **命中一个泛关键词就作答。** 作答门槛改为：至少命中两个关键词，或问题包含标准问题；命中标准问题的知识优先。KB001 的关键词补充了“规则、条件、政策”。
