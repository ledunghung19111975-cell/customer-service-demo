# 电商智能客服开发方案

产出 Agent：Codex。主写与最终收敛：Codex；参与：Codex（代码盘点、业务正确性与范围证据审核）。

状态：待实施的开发设计。本文定义目标行为、改造任务与验收条件；当前运行能力以项目 README 和已有验收证据为准。

## 1. 目标、基线与交付范围

将现有本地客服原型建设为品牌商家的电商服务作品，演示“按商品查询与办理、跨岗位接续、业务结果可核查、质量问题可整改”。继续使用原项目与四个展示入口，不复制第二套应用。

首版保留纯前端、虚构样例与确定性规则。用本地模拟业务状态演示订单、仓库、售后、支付和通知，不接真实接口或资金操作，不新增框架、服务端或第三方依赖。仓库与财务通过责任组及模拟回执参与，不建设完整业务后台。

## 3. 数据结构与状态契约

### 3.1 对象与字段

以下集合及字段为拟新增设计；不是已存在的供应商 API。沿用现有 `customers/staff/orders/knowledge/conversations/cases/tickets/gaps/events`，新增业务集合集中在 `commerce` 内。跨对象引用必须校验客户、订单和明细归属。

| 集合/记录 | 最小字段与约束 |
| --- | --- |
| `orders` | 原 ID、customerId；新记录增加业务来源、事实版本、查询时间；总状态仅概览 |
| `commerce.items` | id、orderId、skuId、商品名、购买数量、币种、实付金额及其来源；金额用整数分 |
| `commerce.payments` | id、orderId、状态、来源、事实版本、查询时间；无权限/未找到/失败作为查询结果，不编造成未支付 |
| `commerce.packages` | id、orderId、明细与数量分配、承运信息、轨迹、异常类型、来源及时间 |
| `cases` | 保留原字段；新增明细/包裹/申请引用、serviceStage、resolutionEvidence、humanParticipation；首次受理和跨会话关系不重置 |
| `commerce.aftersales` | id、caseId、orderId、itemId、数量、类型、原因、凭证引用、规则快照、客户确认、受理回执、审核结论、撤回状态 |
| `commerce.returns` | id、aftersaleId、寄回要求、运单、仓库收货、验收结论和证据；收货与验收独立 |
| `commerce.refunds` | id、aftersaleId、退款义务ID、原请求号、内容指纹、批准金额与来源、执行状态、回执与核实记录 |
| 售后占用 | 按 aftersaleId 记录商品数量、核定金额、预留/累计已用/可释放依据；退款引用同一占用，不能再扣一次 |
| `commerce.handoffs` | id、事项/会话/工单引用、原责任、目标接收人/组、理由、反馈时间、状态、接收历史 |
| `commerce.notifications` | id、事项、目标、内容快照、原发送请求、状态、回执、补救责任；不改变业务结果 |
| `events` | 操作者、业务对象、命令/请求、前后状态、证据引用、时间、是否模拟；不得记真实凭证 |

固定新样例是同一订单的保温杯一件、收纳袋一件，分两个包裹，保温杯签收破损、收纳袋在途。两条实付金额分别为 12900 分和 4900 分，运费为 0、无优惠；这些是虚构测试参数，不从旧订单的 `price` 推导。仅保温杯进入退货退款。规则由样例明确设定，不能表述为所有商家的售后承诺。

新样例使用独立前缀 ID，关联现有演示客户 C001；另保留其他客户订单作为越权反例。新增前先检查碰撞，不覆盖历史同 ID 数据。当前固定客户身份入口可继续使用，不扩建账号系统。

### 3.2 状态轴

| 对象 | 状态及关键守卫 |
| --- | --- |
| 会话 | 沿用 bot/queued/human/closed；关闭只结束本次接待 |
| 事项 | 保留 open/waiting_customer/completed；新增 serviceStage 表示待澄清、处理中、待外部结果、待反馈、异议复核。completed 必须有对应解决证据且无未结异议 |
| 工单 | 保留 new/working/waiting_customer/done；新增 working 下的业务阶段。交接等待用 handoff 表示，不假装已经换负责人 |
| 申请 | accepted、awaiting_material、reviewing、approved、rejected；预览为草稿不落正式申请。撤回轴为 none/requested/unknown/confirmed，不覆盖已发生执行历史 |
| 退货 | awaiting_return、in_transit、received、passed、review_required；验收通过并满足批准条件才允许退款 |
| 退款 | not_submitted、pending、succeeded、failed、unknown；成功只表示模拟渠道回执，未知必须查询原请求 |
| 交接 | pending、accepted、rejected、expired；仅 accepted 移交责任 |
| 通知 | pending、accepted、failed、delivered、unknown；已受理不等于送达 |
| 反馈 | 保留已解决/未解决/未反馈及满意度；没有反馈事件时不得自动填满意或已收到 |

`completeCase`、`updateTicket(done)`、SOP完成、客户反馈和回执处理统一调用同一结果守卫。知识咨询可用明确解决反馈或人工实际完成证据；普通事实查询需确认查询确实回答该诉求；物流异常需核实结论；退货退款需对应批准结果与执行证据。退款未知时，任意文本结果、工单完成或用户反馈都不能制造“退款成功”。拒绝决定可构成该次申请处理结果，但客户异议存在时保持复核。

完成一个协作子任务只记录该任务结果。事项尚未完成时，必须有继续办理的有效责任与反馈时间；不能完成最后一个任务后留下无人负责事项。未完成售后可在已安排责任后关闭会话；历史已完成SOP不能被“不适用”改坏。异议重开服务事项和原工单，成功退款保持成功，已用额度保持占用。

### 3.3 受理、金额及幂等

1. 预览不预留数量或金额。确认命令在同一个状态副本内复查归属、商品、数量、规则、事实版本、已有申请和剩余额度，再同时创建申请、占用、必要工单及事件。单次保存失败，全部不生效。
2. 查重基于客户、订单明细、申请类型及当前申请关系；重访优先显式关联原申请。不能仅凭同订单复用另一商品事项，也不能简单删除整单查重而放开重复受理。
3. `makeCase/aftersalesCase/otherAftersalesTicket`、`intakeToken/intakeFingerprint` 和 `createTicket` 的早返回路径一起改。指纹覆盖客户、事项、订单、明细、数量、类型、原因、凭证、规则/金额/事实版本和确认内容；同请求号同规范内容返回原回执，同号不同内容拒绝。先校验调用人和内容再返回历史回执；已成功请求的合法重放不重新占用，也不因其自身已占用而报额度不足。尚未受理的新请求遇事实变化时重新预览确认。
4. 占用归售后申请统一管理。退款从同一预留转为累计已用，不重复扣减；商品级上限及订单总实付均约束。首版不实现通用分摊，金额来自模拟服务已核定记录。
5. 退款义务与执行请求一一关联。换请求号也不能为同一义务再付款。unknown 只查原请求；failed 保留原申请占用，首版仅允许模拟核实并更新原义务结果，不提供另建独立退款的自动重试。
6. 仅业务确认申请取消/拒绝，且原执行已核实安全终止、没有已执行结果或仍为pending/unknown的任务时，才释放未用预留。申请撤回或拒绝的回执不能替代退款原请求的终止核实；pending/unknown期间继续保留占用，迟到成功回执仍归原义务，不新建第二次退款。审批变化后的额度调整也由模拟服务返回并记录依据。成功金额计入累计已用；本地撤回不能冲销成功退款。
7. 回执核对对象、原请求和单调事实版本；重复只返回原记录，较旧回执保留审计但不覆盖，矛盾终态进入核实。消息到达时间不能代替业务版本判定。

本地实现只保证一次完整状态写入失败时内存不推进。现有 raw 对比保留可检测的陈旧页保护，不是跨标签的原子锁。演示与验收使用单写页面；生产校验占用原子性、回调安全及并发控制属于真实接入阶段。

## 4. 模块与命令

新增 `src/commerce.js`，采用现有 IIFE/CommonJS 双入口风格，纯函数处理模拟事实、金额占用及回执；不直接写存储、不调用网络、不依赖页面，也不反向依赖 domain。`domain.js` 负责角色、事项和工作流，调用 commerce 修改本次状态副本；`store.js` 是唯一正式持久化入口。模拟事件也经过同一命令与校验，不能直接改数组。

在 `index.html` 中将新模块放在 `domain.js` 之前；Node 测试用相应 require。`build_single.py` 已按入口脚本顺序内联，无需第二套打包流程。seed 负责初始样例；更新现有内置规则测试对旧订单号的硬编码依赖。

以下是拟建的领域命令契约，名称供开发统一使用，不是外部接口：

| 命令/现存入口 | 核心输入 | 输出和副作用 |
| --- | --- | --- |
| 查询商品、订单、包裹（扩展 queryOrder） | 调用身份、对象ID、查询范围 | 归属校验后的数据、来源、版本、时间及明确查询结果；查询成功不自动关闭异常事项 |
| previewAftersale | caseId、orderId、itemId、数量、类型、原因、材料 | 可提交预览、金额来源、适用规则、缺项、事实令牌；不创建正式申请 |
| submitAftersale（接入既有确认入口） | 预览内容、令牌、确认、requestKey | 申请/工单/占用/事件一并保存；冲突返回原记录或要求重新确认，不静默修改对象 |
| requestWithdrawal | 申请ID、原请求、理由、当前版本 | 记录撤回请求；confirmed回执到达前保留原状态与占用 |
| supplementAftersale | 申请/事项ID、材料或说明、版本 | 追加原申请与工单，标记责任方有新补充；不重建售后 |
| submitRefund / queryRefund | 申请/退款义务ID、审批引用、原请求 | 校验批准和验收条件；返回执行记录或原流水查询结果，客服不得编辑核定金额 |
| proposeHandoff / acceptHandoff / rejectHandoff | 对象、目标、原因、反馈时间、交接版本 | 提出时保留原owner；接收时重查接手资格、对象版本和未完事项，再统一转移工单、跟进与待办责任 |
| completeCase / updateTicket / closeWithSummary | 对象、结果证据、未完安排、最新版本 | 按第3节守卫分别保存事项/任务结果与会话快照；失败保留输入 |
| applySimulatedReceipt | 事件类型、业务对象、请求、事实版本、预设结果 | 仅演示管理员可触发；事件预设绑定售后/仓库/支付/通知来源并留痕，不赋予客服实际审批权 |

演示管理员的模拟权限需在领域角色表新增，不能仅隐藏按钮。审批、仓库人工验收、财务处理的模拟回执记录“模拟人工办理”及业务角色，计入人工参与；控制面板展示在运营后台现有数据维护内，不增加一级菜单。

## 5. 页面、表单与交互

### 5.1 客户服务与手机端

保留 `#customer`、`#mobile` 和独立面客入口；手机左侧机框、右侧留白，弹层局限机框，两个客户端共用同一份业务记录和草稿。

| 区块 | 展示顺序和操作 |
| --- | --- |
| 订单卡 | 订单号→支付状态→商品/规格/数量→对应包裹→申请与进度入口；查询显示来源时间 |
| 包裹卡 | 包裹及关联商品→轨迹→更新时间→异常说明；“查询轨迹”与“未收到/催发货”分别进入查询或异常事项 |
| 申请表 | 订单→商品→数量→服务类型→原因→材料→补充说明→规则与金额来源；核对预览后提交 |
| 服务进度 | 以事项为单位显示商品、诉求、阶段、下一步、反馈时间；计数与列表使用同一集合，不用cases计数配tickets列表 |
| 售后详情 | 申请→审核→寄回验收→退款→通知→用户反馈，各轴分别显示；可补件、请求撤回或提出异议 |
| 反馈卡 | 明确商品与问题、对应结果及时间；选择已解决/仍需帮助与满意度，不能让用户猜反馈对象 |

点“申请售后”打开表单，不替客户发送一条尚未确认的“申请退货”消息。正式请求确认后才产生申请和受理消息。新咨询不隐藏历史未完事项，用户可从全量本人进度回到原记录；聊天中的补件必须指明关联事项，多个候选时选择后提交。

### 5.2 字段规则

| 字段 | 默认、来源及校验 |
| --- | --- |
| 客户、事项、订单 | 从当前可信上下文带入；客户只读。订单不唯一时不默认选第一笔，只列本人订单 |
| 商品、数量 | 明细列表；首版固定样例数量为1，只允许服务返回的可申请组合。切换订单清除商品/包裹选择与预览令牌 |
| 服务类型 | return_refund、exchange；明确话语可预填但标待核对。含糊“退款”先澄清，不自动理解为必须寄回 |
| 原因、换货要求 | 原因必填1—2000字；exchange时要求必填1—200字，不能预填库存承诺 |
| 材料、说明 | 按样例规则决定材料必需性；首版使用内置虚构凭证引用和说明，不做任意文件上传、OCR或二进制附件持久化；补充说明0—1000字 |
| 规则与金额 | 服务只读返回来源、版本和时间，未知时不显示可提交的确定金额；预览及确认都复核 |
| 转派理由、小结、结果依据 | 必填1—1000字；结果依据还须选择对应业务回执，不能仅靠自由文本完成退款事项 |
| 回访/下次反馈时间 | 需要跟进时必填未来时间；显示日期时分及北京时间UTC+08:00，保存标准时间值，回访负责人继承有效工单责任 |

文本 trim 后校验；必填拒绝全空白，保留内部空格、换行、中文标点和普通表情，按纯文本展示。长度沿用现有JavaScript计数方式并测边界。输入、预览、正式命令均校验；界面校验不能替代领域校验。

预填展示“订单事实/客户原话/待核对提取”。更换商品、类型或规则时保留手填原因与说明，但使受影响的核验与预览失效，重新确认；不能把另一商品金额带入提交。返回修改保留草稿，取消预览不建申请；提交失败保留表单并说明原因。加载、无记录、无权限、查询失败、结果未知、提交冲突分别显示，均保留人工出口。

### 5.3 客服接待与人工协作

保留“会话接待、工单处理”两个菜单及八个SOP节点。SOP按事项展示相关消息、商品、包裹和申请，不能从整段会话首末消息代替该事项证据。四个受理子步骤继续可见；登记受理完成不代表退款完成。

人工请求优先，桌面和手机同规则；区分排队、实际接管、无人可接及离线留言。排队中的规则答复/资料补充不能取消人工请求、重置等待起点或冒充人工首响。人工首响由实际接手后的首次有效人工回复记录。

人工接管后AI只生成草稿，客服编辑并确认发送。新电商运行入口移除自动续答开关；领域层拒绝旧 `setAiAssist/aiContinue` 自动发送，升级时停用旧授权和计时任务但保留历史AI消息。知识或对象依赖改变时建议失效；手写草稿保留但引用需重新核对，不能绑定新版本却发送旧正文。已有输入时仍提供追加/替换/取消。

待处理列表先按人工请求首次等待排序，可切到最近消息；显示等待时长与超时。工单表列依次为事项/商品、业务阶段、工单状态、负责人、待接收目标、首次受理、下次反馈、新补件、操作；支持状态、责任、超时和异议筛选。待客户补充仍展示实际等待，不能静默停掉全部承诺计时；无已批准暂停规则时保留原反馈期限。

转派待接收期间，原owner继续办理；目标可查看接收所需上下文但不能抢先办理。接收成功后一起转移该次明确列出的未完任务和回访责任，历史不改写；旧owner丧失这些任务的办理权。拒绝、超时、目标离线或失去资格时保持原责任并升级经理。初次无人接待由service责任组和经理承担待办，不能有无主受理。接收与原owner同时更新时，通过版本检查要求重新核对。

### 5.4 结束、返回与历史

沉默、切Tab和隐藏手机框不等于离线；显示未回复时长即可，首版不增加自动结束规则。模拟离线保持明确演示标签。关闭面板核对小结、已完成结果及每项未完安排；未完项需要有效责任、工单和反馈时间，纯跟进单不当作售后申请。

关闭面板期间收到新消息或业务结果时，要求刷新核对；关闭、小结、快照和新增跟进记录一次成功后才显示结束。返回、补件和异议接续原事项及工单，保留首次受理、原结果和历史关闭快照；独立新问题另建事项。

## 6. 知识、质量与指标

知识在现有编辑页补充商品/活动适用范围、业务生效与失效时间、规则来源、审核责任和版本。价格、库存、支付、物流与退款从模拟业务查询返回；不从FAQ推断个人资格或实时状态。旧交易规则不可查时交人工核实，不能套用当前规则。

知识发布仍走草稿→正反例→发布→入口验证→原问题复验。测试依赖指纹包含草稿内容、适用范围、有效期、样例和接待规则版本；修改即作废旧结果。过期规则不能直接回滚生效，错误版本先停用，保留人工出口。

质检根因分为知识、检索/路由、业务查询、办理流程、协作和通知；知识类关联版本，其他类型关联对应修复记录与失败用例。现有仅调用 `classify` 的单条测试不能代替完整会话/业务命令验收。只有原失败路径与必要反例均有证据才能关闭整改。

管理看板以同一受理时间队列、同一观察截止点的有效事项统计，显示范围和待观察数量，所有卡片可下钻。排除纯寒暄、垃圾和明确测试样本；演示样本用独立“演示数据”范围展示，不冒充真实运营。

| 指标 | 计算约束 |
| --- | --- |
| 解决率 | 对应诉求解决证据成立且无未结异议÷同批有效事项；处理中、未知仍在分母，未反馈且无其他证据不算成功 |
| AI独立解决率 | 已解决且无实质人工核实/办理÷同批有效事项；人工审批、验收和财务办理排除分子，事后抽检不算办理 |
| 人工首响 | 请求人工到实际接手后首次有效人工回复；AI和排队提示不停止计时，转派不重置起点 |
| 处理时长 | 首次受理到有依据办结，异议保留起点；未完、补件和外部等待单列 |
| 满意度与反馈率 | 只统计明确反馈；未反馈、未解决和渠道成功分别记录 |

不从未转人工率推算解决率，不预填成本节省或成效数字。退款渠道成功可提供执行证据，但不能自动生成用户已收到或满意的反馈。

## 7. 数据升级与历史兼容

采用新存储键 `qinghe-support-ecommerce-v1`、顶层schema 5；这些为拟新增设计。原 `qinghe-support-v4` 及其文案备份保持原字节不变，v3键不自动导入。数据升级不修改原V4存储，旧页面继续使用旧键也不能覆盖电商数据。

初始化优先读取已经存在的新键。新键无效时停止写入并展示恢复/导出说明，不以seed重置；只有新键不存在才尝试迁移有效V4，原V4不存在才创建新样例。存在但损坏的V4必须保留并报错，不把损坏误当没有数据。

迁移步骤：读取并验证V4原值→原字节备份并回读→在内存转换和加入无冲突样例→schema5验证→再次核对源值未变且目标仍不存在→一次写入目标→回读验证→进入工作区。任一步失败不改变源；目标写入后回读失败进入恢复状态，不能自动覆盖目标重跑。备份沿用已有“相同原值复用、不同原值加后缀、永不覆盖”方式。新旧数据之后不自动双写或合并；源变化提示存在独立历史记录。

| 旧数据 | schema5兼容行为 |
| --- | --- |
| 原集合、ID、关系、消息、备注、回执、首次时间、结果与关闭历史 | 全部保留；迁移元数据登记历史ID集合，不改写业务历史 |
| 旧case/ticket状态 | 沿用原枚举和历史语义；不推导新serviceStage的业务成功，不合成退款回执 |
| 缺少followupOnly的旧工单 | 保持“历史已受理”语义；显式followupOnly仍是跟进单 |
| 缺明细、金额来源和包裹的旧订单 | 显示原摘要及“历史通用记录”；只读回看，不进入新售后/退款命令 |
| 旧未完、已完成和已重开事项 | 状态和责任完整保留，独立历史区域展示，不混入电商演示队列与指标，也不自动标记已解决 |
| 旧知识/策略 | 历史版本保留；电商样例使用经过独立测试的显式适用规则，旧通用规则不自动认定适用于新商品 |
| `sessionStorage` 的 `qinghe-support-view` | 原值保留并复制为历史快照；新UI使用独立键 `qinghe-support-ecommerce-view-v1`，不将旧草稿绑定到新商品 |

历史只读集合限定为导入的订单、会话、事项、工单、知识/策略版本、质量记录与事件；不冻结复用的customers/staff主数据。C001恢复在线、坐席调整可接待状态等命令可修改schema5的当前运行态并记新事件，原V4、迁移备份、历史会话和历史事件不变；不因导入时离线或不可接待而永久阻断新电商流程。

历史业务记录在新入口只读，不提供继续退款或修改既有业务结论的按钮；领域命令同样拒绝修改这些历史对象。新服务可建立显式关联的咨询事项并人工核实，首版不将无明细历史交易转为可执行电商订单。新旧关联仅作追溯，不复制受理或执行结果。`legacy.html` 只服务v3，不充当V4恢复入口。

保留源sessionStorage实际已保存的草稿内容供查看；未持久化的内存草稿不承诺恢复，实施升级前提示先保留。旧AI授权只保存为历史，不恢复发送许可。新数据的草稿按身份、会话、事项和表单隔离。

回退代码前先导出/保留当前电商原始快照；恢复旧版本只读写旧V4键，不能把电商新记录反向覆盖旧键。重新启动电商版仍读取已存在的新数据。回滚不等于删除新键、丢弃新增记录或重置业务。
