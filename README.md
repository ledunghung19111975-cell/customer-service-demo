# 智能客服工作空间

产出 Agent：Codex。集成、主写、参与与最终收敛 Agent：Codex。用户附件原始产出平台未标明。视觉主题层 `src/theme.css` 产出 Agent：Claude（2026-10-05）。

智能客服是面向电商服务场景的本地交互原型。客户服务、客服工作台、运营后台共用一份会话、客户问题、工单与知识记录；“手机端演示”是同一客户角色的另一种展示模式。原型展示从咨询到办理、从服务问题到知识整改的完整操作链。面客页面使用“服务中心”和“在线客服”，样例身份使用客户编号与客服 01 / 02。

## 本地运行

在项目目录执行，需 Python 3，无需安装 npm 包：

```bash
python3 run.py --no-open
```

服务仅监听本机 `127.0.0.1:8768`。省略 `--no-open` 会自动打开浏览器；按 `Ctrl+C` 停止。端口被占用时会退出并提示，不自动换端口。

| 入口 | 地址 |
| --- | --- |
| 客户服务，默认工作区 | [客户服务](http://127.0.0.1:8768/#customer) |
| 手机端演示，与客户服务共用记录 | [手机端演示](http://127.0.0.1:8768/#mobile) |
| 客服工作台 | [会话接待](http://127.0.0.1:8768/#desk/inbox) |
| 运营后台 | [服务概览](http://127.0.0.1:8768/#ops/overview) |
| 独立客户页面，无工作区切换 | [服务中心](http://127.0.0.1:8768/?view=customer#customer) |

演示时使用同一标签页切换工作区。后台入口按照当前运营角色显示可用页面；服务概览属于“服务经理”。角色切换用于演示岗位职责，不是登录认证。

## 电商客服演示

电商入口为[客户服务](http://127.0.0.1:8769/?data=ecommerce#customer)。运行 `python3 run.py --port 8769 --no-open` 后可查看。客户服务、手机端演示、客服工作台和运营后台共用新电商工作空间；默认入口继续打开 V4。

固定样例为同一订单的保温杯一件（12900 分）与收纳袋一件（4900 分），实付 ¥178、无优惠和运费。保温杯包裹已签收，收纳袋包裹在途。客户页与手机页可查看商品、支付、两个包裹及事实来源、版本和时间；查询失败与结果未知不会显示成未支付。签收未收到等异常保留人工核实路径。

电商数据保存于 `qinghe-support-ecommerce-v1`（schema 5），草稿保存于 `qinghe-support-ecommerce-view-v1`。电商入口不读取、迁移或改写 V4 数据和草稿；旧 V4 原值可由系统管理员在数据维护页导出。新键损坏、初始化保存失败或写后回读异常时停止进入业务页面，提供原始保存值导出，禁止用样例覆盖；普通操作保存失败保留原状态并提示。不同访问端口的数据彼此独立。

电商流程支持以下行为：

- 规则咨询由实际适用的商品规则生成金额、经理审核与寄回验收要求；咨询不建申请。“收纳袋没到，保温杯破了想退”分别创建两个未决商品事项。
- 保温杯一件退货退款：客户填写与预览 → 主动确认 → 经理批准、拒绝或要求补件 → 客户寄回 → 管理员模拟仓库收货与验收 → 负责客服提交原退款请求 → 独立模拟退款、通知回执 → 客户反馈。
- 预览不占用数量或金额；确认创建一次占用，重复同请求重放原结果。结果未知只核对原流水，失败须安全终止证据后才能确认撤回并释放未用额度；成功退款与已用额度保留。
- 事项、申请、验收、退款、通知与客户反馈分别显示。异议继续原事项并保留原结果；通知失败不改写退款。已经完成的事项通过“仍需帮助”进入复核。
- 人工交接为待接收、接收、拒接或超时。接收前原人继续负责；接收后同步事项及办理工单责任。新负责人可发事项公开回复，关闭会话后仍能继续跟进；经理可核对超时交接。
- 知识与策略发布需正反例及 12 个实际多轮业务场景通过，依赖变化或规则过期阻止发布。质量整改按根因分类，验收对应原事项的业务、交接或通知证据，多商品必须全部核对。
- 服务概览提供 10 个可下钻事项指标，查询、受理、办理完成、退款成功、客户确认、AI 独立完成与人工参与各有独立口径。模拟数据不代表真实经营效果。

人工接管后默认由客服核对草稿并发送；自动续答演示开关保留且默认关闭，不办理退款。完整操作见 [演示脚本](docs/演示脚本.md)，当前验证见 [验收矩阵](docs/验收矩阵.md)。

## 通用 V4 行为

- 客户咨询支持本地知识答复、本人订单查询、售后申请、历史咨询与处理进度。手机 Tab 在左侧手机框内提供相同流程，右侧留白，共用当前咨询与未发送草稿。
- 客服右侧 SOP 常显“确认诉求、核对订单、查询物流、退换货办理、补充资料、记录处理结果、回访安排、结束沟通”八个节点；退换货四个子步骤始终可见，多问题分别跟进。
- 退换货申请包含订单、类型、原因、换货要求与补充说明；预填须核对，先预览再确认。取消不建单，重复确认继续原记录。关闭时建立的纯跟进工单不代表售后已经登记。
- 客服先接管再回复；公开回复与内部备注分开。能够当场解决的问题可直接记录结论和内部依据，需要后续办理的问题再建工单。
- 人工接管后 AI 自动续答默认关闭。客服明确开启后等待 30 秒，单次授权最多 2 轮，每轮须有新客户消息；输入、回复、暂停、转派、关闭和离线会停止待发送内容。AI 消息标识“AI 协助”，不计人工首响，不办理退款。
- 客户模拟离线后，客服逐项安排未完成事项，再保存小结和关闭快照。回访依附工单，继承负责人；未联系上须重新安排未来时间，回访结果不自动办结业务。
- 处理结果与客户反馈分别记录。客户提出异议后继续原问题、重开原工单，保留首次受理时间；结束沟通不会清空办理记录。
- 运营后台分为服务经理、知识运营、系统管理员三个角色。知识和接待策略经过草稿、回归、发布；质量问题经过复核、整改、原问题验证后验收。
- 接待策略可配置人工触发词与售后受理开关，使用固定服务路径。草稿查询故障只作用于当次隔离测试。

## 数据与实现边界

V4 使用浏览器保存键 `qinghe-support-v4`。数据依赖浏览器及访问地址；不同协议、主机或端口的数据不共享。写入失败不更新当前业务状态；发现其他页面改写后会拒绝旧页面覆盖，提示刷新，但不提供多人并发保证。

`src/copy.js` 对已有 V4 数据中的指定内置默认文案做精确更新，保留会话、订单、工单编号及业务关系，保留手写消息、备注和草稿。更新前将原始保存值原样备份到 `qinghe-support-v4:before-copy-v1`；相同原值可复用已有备份，不同原值使用 `:1`、`:2` 等后缀另存，已有备份不覆盖。备份或校验失败时停止更新。内置知识来源变化会使知识与策略的缓存回归结果失效，需要重新验证。

旧保存键 `zhixu-customer-demo-v3.1` 保留，不自动导入 V4。需要查看旧数据时访问 [旧版入口](http://127.0.0.1:8768/legacy.html)；它运行旧模块，修改只属于旧版。系统管理员也可从“数据维护”导出旧版原始保存值。

**当前问答使用关键词与确定性规则，业务数据来自虚构样例。** 没有真实模型、RAG、后端身份鉴权、外部订单、支付退款、短信邮件、多租户或跨设备同步。客户页面隐藏内部信息属于本地视图约束，不能作为生产安全隔离。记录办理结果不会执行退款。请勿录入真实客户资料、凭证或支付信息。

## 构建与验证

生成自包含 HTML：

```bash
python3 build_single.py
```

输出为 `dist/智能客服.html`。日常运行和持久化验收使用上面的 HTTP 地址；直接打开文件时的浏览器存储行为需要单独验证。

逻辑测试需 Node.js：

```bash
node --test tests/domain.test.cjs
node --test tests/workflow.test.cjs
node --test tests/v4-ui.test.cjs tests/workbench-ui.test.cjs tests/workbench-review.test.cjs
node --test tests/copy.test.cjs
node --test tests/*.test.cjs
```

`tests/domain.test.cjs` 与 `tests/workflow.test.cjs` 验证业务域、SOP、授权、受理、关闭、回访与保存逻辑；三份界面测试加载当前入口并用 VM 驱动事件和可控计时器，`tests/copy.test.cjs` 验证默认文案更新、原始值备份及用户内容保留。全量命令还会运行旧根模块测试，不能把总通过数写成 V4 覆盖数。旧 `tests/browser_smoke.py`、`tests/product_browser_smoke.py` 及旧 evidence 不适用于 V4。真实浏览器验收状态与证据范围见 [验收矩阵](docs/验收矩阵.md) 与 [SOP/手机端验收证据](tests/evidence/sop-mobile-review.json)。真实 iOS 键盘、设备网络与通知未验证；JSON 导出下载落盘和再次读取未作为已通过结论。

电商改造的目标能力与开发顺序见[电商改造开发方案](docs/当前方案与角色分工修改计划.md)。该方案按阶段实施；已验证能力与后续目标在电商预览说明及执行记录中分别标明。
